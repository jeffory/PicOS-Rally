# GitHub Actions CI and initial prerelease

Date: 2026-07-28
Status: approved, ready for implementation planning
Repo: `jeffory/PicOS-Rally` (public, default branch `main`, no tags at time of writing)

## Goal

Continuous build and test on every push and pull request, plus a tag-triggered
job that packages an installable app bundle and publishes it as a GitHub
prerelease. First release to cut: `v0.5.0`.

## Background

The repo builds two targets today, both by hand:

- `make` at the repo root cross-compiles `main.elf` for Cortex-M33 with
  `arm-none-eabi-gcc` (PIE, custom linker script at `sdk/native/linker.ld`).
- `plat/headless/` builds with host gcc and produces `rally_headless`, a
  TAP-emitting test runner whose exit code is the failure count. Its header
  comment already states it is CI-gateable. It currently passes 51 of 51
  checks covering the tyre model, load transfer, surface lookup, input ramps,
  sim determinism, tilemap, gfx, audio synth and effects.

Baked assets (`assets/*.bin`) and the stage blob (`stage01.bin`) are committed,
so CI needs no Python art or track bake step. `main.elf` is gitignored.

There is no `.github/` directory and no existing automation.

## Decisions

| Question | Decision |
| --- | --- |
| Release artifact | Installable app bundle zip, laid out as the on-device app dir |
| Trigger | Push of a `v*` tag |
| Version source of truth | The tag. CI fails if `app.json` disagrees |
| Continuous side | Separate `ci.yml` on push and pull request |
| Toolchain acquisition | Pinned ARM tarball, SHA256 verified before use |
| Initial version | `0.5.0`, plain semver, GitHub prerelease flag |
| Bundle definition | Owned by `tools/bundle.py`, shared with `rally_hw.py` |
| Build provenance | Included, via `actions/attest-build-provenance` |

### Why plain semver rather than a prerelease suffix

`app.json`'s version string is consumed by the PicOS launcher, which lives in
the PicOS repo and is not vendored here, so the strictness of its parser cannot
be verified from this repo. A plain three-part version removes the risk
entirely. Prerelease status is carried by GitHub's own flag, which is
independent of the version string.

`0.5.0` reflects that M0 to M5 are complete and M6 closes 1.0, per
`ROADMAP.md`.

## Findings that shape the design

Two facts discovered while exploring, both of which a naive implementation
would get wrong.

**The runtime asset set is narrower than `assets/`.** `load_assets()` at
`app/main.c:144` opens exactly eight files: `clut.bin`, one tile binary per
entry in `TILE_SEC_NAMES`, and `car.bin`, `props.bin`, `hero.bin`.
`core/tiles_sections.h:4` currently names four sections: `wang_water_sand`,
`wang_sand_grass`, `wang_grass_gravel`, `proc`. The three `tiles_path_*.bin`
files are dead since M4 replaced the RPG path tiles with the procedural road,
and the `.bin.json` sidecars plus `atlas.json` are bake metadata the app never
reads. An `assets/*.bin` glob would over-ship.

**The existing push filter is stale.** `push_app()` at `tools/rally_hw.py:101`
zips only files named `main.elf`, `app.json`, `handling.toml` and
`stage01.bin`. It captures no assets at all. Deploys currently work only
because assets were pushed to the device at some earlier point and persist on
the SD card. This is exactly the drift that a second, independent bundle
definition in a workflow file would perpetuate.

## Architecture

New files: `tools/bundle.py`, `tools/test_bundle.py`,
`.github/workflows/ci.yml`, `.github/workflows/release.yml`.
Modified: `tools/rally_hw.py` (reuse `collect()`), `.gitignore`, `app.json`
(version bump).

Three units, each with one responsibility.

### `tools/bundle.py`

The single definition of what a PicOS Rally app bundle contains. Importable and
runnable.

```python
collect(app_dir) -> [(source_path, arcname), ...]
```

```
python3 tools/bundle.py --out dist/PicOS-Rally-v0.5.0.zip [--expect-version 0.5.0]
```

Bundle contents, twelve files, mirroring the on-device app dir:

```
main.elf
app.json
stage01.bin
assets/clut.bin
assets/tiles_wang_water_sand.bin
assets/tiles_wang_sand_grass.bin
assets/tiles_wang_grass_gravel.bin
assets/tiles_proc.bin
assets/car.bin
assets/props.bin
assets/hero.bin
tuning/handling.toml
```

Paths are fixed by the app and must not change:
`<app_dir>/assets/<name>` (`app/main.c:116`),
`<app_dir>/tuning/handling.toml` (`app/main.c:180`),
`<app_dir>/stage01.bin` (`app/main.c:196`).

Behaviour:

- Tile section names are parsed from `core/tiles_sections.h`, not hardcoded.
  That header is generated by `trackbake.py` from `atlas.json`, so a future
  stage that changes the terrain chain updates the bundle automatically.
- `main.elf` is resolved as the repo-root file explicitly. `sdk/native/main.elf`
  exists as a vendored SDK example and must never be picked up.
- Every asset that appears in `assets/manifest.json` is checked against its
  recorded `bin_sha256`.
- `clut.bin` is checked for exactly 512 bytes, because `load_bin()` at
  `app/main.c:122` rejects a size mismatch and the game fails at startup.
- When `--expect-version` is supplied, `app.json`'s `version` field must equal
  it, otherwise exit non-zero.
- Any missing file is a hard failure.
- Zip entries are written in sorted order with a fixed timestamp, so identical
  inputs produce a byte-identical archive. This lets a downloaded release asset
  be compared against a local build.

`push_app()` in `tools/rally_hw.py` is rewritten to call `collect()`, replacing
the stale filter. Deploy-to-hardware and ship-a-release then package
identically.

### `.github/workflows/ci.yml`

Triggers on push to `main` and on all pull requests. A concurrency group keyed
on the ref cancels superseded runs.

Two jobs, run in parallel:

- `test`: build `plat/headless` with the runner's host gcc, run
  `./rally_headless`, fail on non-zero exit. Then run `tools/test_bundle.py`,
  which is hermetic and needs no ARM build.
- `build`: install the pinned ARM toolchain, run `make`, print
  `arm-none-eabi-size` output so binary growth is visible in the log.

### `.github/workflows/release.yml`

Triggers only on tags matching `v*`. Single job.

1. Checkout at the tag.
2. Install the pinned ARM toolchain.
3. Run the headless suite and the bundle tests as gates.
4. `make` to produce `main.elf`.
5. Derive the expected version by stripping the leading `v` from the tag, then
   run `bundle.py --expect-version` so a tag disagreeing with `app.json` fails
   before anything is published.
6. Write `SHA256SUMS` next to the zip.
7. Attest build provenance for the zip.
8. `gh release create --prerelease` with auto-generated notes, attaching the
   zip and `SHA256SUMS`.

## Toolchain pinning

Pinned release: **ARM GNU Toolchain 14.3.rel1**, x86_64 host, `arm-none-eabi`
target. This is the newest release ARM publishes; 14.4 and 15.x do not exist as
of 2026-07-28.

```
URL:    https://developer.arm.com/-/media/Files/downloads/gnu/14.3.rel1/binrel/arm-gnu-toolchain-14.3.rel1-x86_64-arm-none-eabi.tar.xz
SHA256: 8f6903f8ceb084d9227b9ef991490413014d991874a1e34074443c2a72b14dbd
```

That hash is ARM's own published checksum, retrieved over HTTPS from the
`.sha256asc` file alongside the tarball. Implementation confirms it against an
actual download before committing the workflow, so the pin is verified rather
than merely copied.

Both workflows read the URL and hash from a single shared definition so they
cannot diverge. The tarball is verified with `sha256sum -c` before being placed
on `PATH`, and cached with `actions/cache` keyed on the hash.

Note that 14.3.rel1 differs from the local Fedora `arm-none-eabi-gcc 15.2.0`,
and no ARM release matches a distro build, so the two cannot be reconciled. The
consequence is covered under Limitations.

## Security posture

The repo is public and will publish executables, so the workflow is also a
supply chain surface.

- Top-level `permissions: contents: read`. The release job additionally gets
  `contents: write`, plus `id-token: write` and `attestations: write` for
  provenance. No other job holds a writable token.
- Every action pinned to a full commit SHA rather than a movable tag such as
  `@v4`.
- Trigger is `pull_request`, never `pull_request_target`, so a forked pull
  request cannot reach a writable token.
- Only the built-in `GITHUB_TOKEN` is used. There are no repository secrets, so
  a compromised workflow leaks no credentials.
- The toolchain tarball is checksum-verified before execution.
- `actions/attest-build-provenance` produces a signed SLSA provenance record
  binding the published zip to the commit and workflow run that built it, so a
  downloader can verify the artifact was not substituted.

## Testing

`tools/test_bundle.py` emits TAP, matching the convention `plat/headless`
already uses, and runs in `ci.yml`.

It is hermetic: each case builds a throwaway app dir in a temp directory,
copying in the real `assets/`, `stage01.bin`, `tuning/` and `app.json` and
writing a stub `main.elf`. This matters for two reasons. The `test` job builds
only the host target, so no real `main.elf` exists there and a test against the
working tree would fail. And the tampering cases cannot be expressed at all
without a scratch copy, since they require corrupting an asset the repo must
keep intact.

It asserts:

- `collect()` returns exactly the twelve expected entries.
- `collect()` never returns `sdk/native/main.elf`, the mistake a glob makes.
- A version disagreeing with `--expect-version` exits non-zero.
- A tampered asset byte fails the manifest SHA256 check.
- A `clut.bin` of any size other than 512 bytes is rejected.
- A missing file is a hard failure.
- Two runs over identical inputs produce byte-identical zips.

`ci.yml` is validated by opening a pull request.

`release.yml` cannot be meaningfully dry-run. Before cutting the tag: build the
bundle locally, unzip it, push it to the PicoCalc with `rally_hw.py`, and
confirm Cooloola Point loads and runs from the bundle contents alone. This is
the check that proves the twelve-file list is complete, and it must pass before
`v0.5.0` is tagged.

`.gitignore` gains `dist/` and `plat/headless/scene`. The former is a new build
output directory, the latter is currently untracked but unignored.

## Release procedure

`app.json` currently reads `0.1.0`. It must be bumped to `0.5.0` and committed
**before** the tag is pushed, otherwise the version gate correctly rejects the
release. The full order:

1. Bump `app.json` version to `0.5.0`, commit to `main`, confirm CI is green.
2. Build the bundle locally: `python3 tools/bundle.py --out dist/PicOS-Rally-v0.5.0.zip --expect-version 0.5.0`.
3. Unzip it to a scratch dir, deploy with `RALLY_APP_DIR=<scratch> rally_hw.py push`,
   and confirm Cooloola Point loads and is drivable from bundle contents alone.
4. Tag and push: `git tag v0.5.0 && git push origin v0.5.0`.
5. Download the published zip, verify it against `SHA256SUMS`, and smoke-test
   that exact artifact on hardware.
6. Only then announce.

Steps 3 and 5 are not redundant. Step 3 proves the file list is complete using
a locally built binary. Step 5 proves the CI-built binary, compiled by a
different toolchain, actually runs.

## Limitations

Stated explicitly so they are not mistaken for guarantees.

**The published binary has never been executed.** It is compiled by ARM's
toolchain on a GitHub runner, not by the local Fedora `arm-none-eabi-gcc
15.2.0`, and no ARM-side tests run in CI. Green CI means it compiled, linked,
and the host-side sim still passes its 51 checks. The release zip must be
downloaded and smoke-tested on hardware before the release is announced.
Publishing and announcing are separate acts.

**Owed human verification is still outstanding.** `ROADMAP.md:39` records an
unfinished ear test covering engine pitch, gravel roar level and event balance,
plus M4 visual checks on gravel hue and sand contrast. This is acceptable for
something flagged prerelease, but the release notes should say so rather than
let a downloader assume the game is tuned.

**Published tags are awkward to move.** The version gate catches the likeliest
failure before publish. Beyond that, the answer to a bad release is to cut
`v0.5.1`, not to retag.

**`clut.bin` is not covered by manifest hashing.** It has no entry in
`assets/manifest.json`, so only its 512-byte length is checked. Adding it to
the manifest is a `palettize.py` change and is out of scope here.

## Out of scope

- Any change to the art or track bake pipeline.
- Adding `clut.bin` to `assets/manifest.json`.
- Hardware-in-the-loop testing from CI.
- Release automation for the PicOS repo itself.
- The M6 work described in `ROADMAP.md`.
